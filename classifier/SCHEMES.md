# 题目难度的算法方案

给每道题算一个 **1–20 分制难度**（20 = 平均的 AMC 12 第 25 题，AIME/奥赛在其上方）。这份文档只谈"怎么算"，字段怎么存见 `docs/paper-format.md` §4.6，跑批工具见 `classifier/README.md`。

结论先放前面：

| 方案 | 数据依赖 | 今天能不能用 | 单题成本 | 适合阶段 |
| --- | --- | --- | --- | --- |
| **A. 竞赛×题号先验** | 无 | ✅ 已实现 | 0 | 冷启动、兜底 |
| **B. LLM 规则量表** | 无 | ✅ 已实现 | ~4s / 题 | 冷启动主力 |
| **C. Elo** | 逐题对错 | ❌ 缺数据流 | 0 | 有作答后 |
| **D. IRT（2PL）** | ≥200 次/题 | ❌ 缺数据流 | 0 | 数据成熟后 |
| **E. 人工锚点** | 人工时间 | ⚠️ 少量可以 | 高 | 校准、验收 |

现在能立刻落地的是 **A + B 融合**（`classifier/difficulty/` 里已经写好）。C/D 不是算法难，是**数据没采**——`/api/result` 目前只存整卷聚合分，一道题的作答记录都没有。所以真正的第一步是让前端把逐题对错传上来，否则 C/D 永远算不了。

---

## 1. 难度是拿来干什么的

先明确用途，否则"难度"会变成一个谁都不服的玄学数字：

1. **组卷配比**——出了张卷子太简单/太难，要能按 level 重新抽。
2. **自适应推题**——学生做对 L3，下一题给 L4；做错 L3，退到 L2。
3. **进度曲线**——"你最近 30 天做对的题平均难度从 2.1 涨到 2.8"，这比分数百分比有意义得多。

这三种用途只需**相对排序正确**，不需要绝对标定。所以别指望一开始就准，先保证单调性可用。

## 2. 统一口径

存进 schema 的不是一个数字，而是一次**带来源的估计**（字段定义见 `docs/paper-format.md` §4.6）：

```jsonc
"difficulty": {
  "level": 15,                      // 主结果，1-20 整数，下游只认这个
  "scale": "amc20",                 // 标尺代号，旧 1-5 结果标 legacy5
  "band": "medium",                 // <=9 easy / 10-17 medium / >=18 hard
  "score": 14.6,                    // 1-60 连续分，排序、插值用
  "method": "hybrid",
  "confidence": 0.62,
  "components": [                   // 每路来源各记一条，可解释、可重算
    { "method": "prior",      "score": 13.90, "weight": 0.35 },
    { "method": "llm_rubric", "score": 15.00, "weight": 0.65 }
  ],
  "evidence": { "attempts": 0 },
  "reviewed": false
}
```

**1–20 标尺**（LLM 侧用的就是这张表，也是人工标注的锚）：

| level | 锚点题 | 典型特征 |
| --- | --- | --- |
| 1 | AMC 8 #1 | 一步直取：代公式、读表、一次四则运算 |
| 3 | AMC 8 #8 | 两步常规，一个公式 |
| 5 | AMC 8 #15 | 标准课本方法 + 小分类 |
| 7 | AMC 8 #22 ≈ AMC 10 #4 | 两个想法组合 |
| 9 | AMC 10 #12 | 需要选对工具 |
| 11 | AMC 10 #19 | 三步 + 一个轻观察 |
| 13 | AMC 10 #25 ≈ AMC 12 #10 | 多步综合 |
| 15 | AMC 12 #15 | 真综合，需关键观察 |
| 17 | AMC 12 #20 | 构造或细致分类讨论 |
| 19 | AMC 12 #24 |  |
| **20** | **AMC 12 #25** | **锚点：平均的 AMC 12 压轴** |
| 23 | AIME #1–#5 | 需要真想法，路径短 |
| 27 | AIME #8–#11 | 中段 AIME |
| 30 | AIME #14–#15 | 难 AIME |
| 34 | 奥赛短名单 / USAMO #1–#2 |  |
| 38 | USAMO #3–#6、IMO #1–#3 |  |
| 42+ | IMO #6 级 | 仅在题目确实如此时使用 |

明确**不**作为依据的三件事：题干长度、数字好不好算、解析写得多长。

## 3. 方案 A：竞赛 × 题号先验（确定性，零成本）

同一竞赛的卷子里，第 1 题永远比第 20 题简单——这是出题人替我们做好的标定。用两个参数就能拟出很不错的基线：

```
t       = (position - 1) / (positions - 1)      # 0…1，卷面位置归一
score   = BASE[competition] + SPREAD[competition] * t
level   = to_level(score)                         # <1.5→1, <2.5→2, <3.5→3, <4.5→4, else 5
```

`BASE`（该赛事第一题的难度）与 `SPREAD`（到最后一题涨多少）在 `classifier/difficulty/prior.py` 里，例如：

| 竞赛 | BASE | SPREAD | 依据 |
| --- | --- | --- | --- |
| mathcounts / amc8 | 1.4 | 1.4 | 入门赛事，卷内跨度小 |
| amc10 | 2.2 | 1.6 | 1-10 送分，11-20 分水岭，21-25 压轴 |
| amc12 | 2.7 | 1.6 | 同结构但整体上移 |
| aime | 3.6 | 1.0 | 15 题整体都在 3-5 |
| usamts / cmo / bpho | 3.2–3.4 | 1.0–1.2 | 长题、证明题，位置信息弱 |

**优点**：零成本、确定性、可复现、对新题也成立（新题也有 position）。
**缺点**：只能表达"这份卷子里靠后"，无法区分同位置的题——AMC 10 第 21 题可能比第 25 题难；同一年份的运气波动、跨年份差异都吃不到。
**验收**：与人工标注的 Spearman 相关系数；经验值在 0.5–0.65 之间就算合格基线。

## 4. 方案 B：LLM 规则量表（当前主力）

把 §2 那张量表 + 你的考点目录（433 节点）一起塞给模型，让它输出 `{primary, tags, difficulty, difficulty_confidence, why}`。

关键工程约束（都踩过）：

- **必须在 prompt 里禁止"按长度/数字/解析长度"打分**，否则模型会把长题一律判 4–5 级，这是最常见的失效模式。
- 要求它给 `why`（≤25 词），并且 `why` 里必须提到**具体的那一步**。`why` 是事后抽检的唯一便宜手段。
- 只给 position、告诉它卷面题数（`positions_in_paper`），但明确写"位置仅供参考"，让它自己判断——纯按位置打分的模型等于退化成方案 A。
- **不要用结构化输出**（`response_format: json_schema`）——这台推理服务器上会把内容打坏成 `{"primary":": "`，见 `classifier/llm.py` 顶部注释。用提示 + 本地 JSON 修复。
- 长几何题会出现"思考把 max_tokens 吃光、content 为空"，`llm.py` 里的 `_starved()` 会自动加倍预算重试；这类题不算失败。

**成本**：实测 ~4s/题（concurrency 4，reasoning_effort=low，前缀缓存命中 99.9%），9266 题全库约 3–5 小时。
**一致性**：temperature 0.1，同一题重跑 level 一般稳定（抖动 ±1 级约占 10–15%），靠 `confidence` + `components` 记录，低置信度的进人工抽检队列。
**验收**：抽 50 题人工标 1–20，看 Spearman（通常 0.7–0.8）与混淆矩阵；特别检查 4/5 级有没有被滥用。

## 5. 方案 C：Elo（要作答数据）

把题当"选手"，学生当"对手"：

```
期望得分 E = 1 / (1 + 10^((D_item - R_user) / 400))
D_item' = D_item + K * (S - E)          # S = 1 答对 / 0 答错
R_user' = R_user + K * (E - S)
```

- 题目初始分用 A+B 的 `score` 折到 Elo 量纲（`D = 1000 + 250 * score`），**不要从 1200 起步**，否则前几百次作答全在还债。
- `K` 随作答次数衰减（`K = 40 / (1 + attempts/30)`），否则早期一次运气作答会把题永久推歪。
- 只统计**同一次考试内**的作答（避免同一学生刷同一题）。
- 需要的数据：`qid`、用户、对错、时间戳。`qid` 我们已经有了（迁移时生成了 9266 个稳定 id），所以只差"逐题上报"。

**优点**：自动随学生水平漂移校准，不需要人工；比 LLM 更客观。
**缺点**：冷题无数值；学生群体水平分布偏斜时会有系统性偏移；一道题被强学生做错会被高估。
**验收**：与 B 的 Spearman ≥ 0.6 即说明两者不冲突；走势单调（同考点内随年份难度应平滑）。

## 6. 方案 D：IRT 2PL（数据成熟后）

比 Elo 多一个"区分度"参数，能识别"这题要么会要么全错"（区分度高）和"人人蒙"（区分度低）：

```
P(correct | θ) = 1 / (1 + exp(-a * (θ - b)))
```

- `b` = 难度（就是我们要的 level），`a` = 区分度。
- 经验门槛：**每题 ≥200 次作答**才稳定；≤30 次时估计值方差极大，不上。
- 实现成本：需要 EM 或 MCMC 拟合（Python 侧要引入 numpy/scipy——**这会打破仓库"零依赖"的规矩**，建议放到独立离线脚本里跑，结果只回写 JSON，服务端不依赖）。
- 收益：一旦有了 `a`，自适应推题的准确度显著好于 Elo。
- 建议：等全库累计作答 >20 万条再考虑，现在做纯属过度设计。

## 7. 方案 E：人工锚点（校准用，不是主力）

不需要标全库，只需要 **200–300 道锚题**：

- 覆盖 8 个板块 × 5 个等级，每个格子至少 5 题；
- 人工标的 `reviewed: true` 的题会**直接覆盖**自动值（`combine.py` 里 `human_score` 权重独占）；
- 用锚题去校准 A/B：拟合 `human ≈ f(prior, llm)`，得到两个来源的实际可信权重——比拍脑袋写 0.35/0.65 强。

## 8. 融合：分阶段权重

`classifier/difficulty/combine.py` 按"这道题被做过多少次"切四个阶段：

| 阶段 | 条件 | prior | llm_rubric | elo | irt |
| --- | --- | --- | --- | --- | --- |
| cold | attempts = 0 | 0.35 | 0.65 | – | – |
| early | 1–9 | 0.20 | 0.50 | 0.30 | – |
| mid | 10–29 | 0.10 | 0.35 | 0.35 | 0.20 |
| mature | ≥30 | 0.05 | 0.20 | 0.35 | 0.40 |

原则：**数据越多，越信实测，越不信先验**。`prior` 从 0.35 一路降到 0.05 而不是归零——它是唯一不依赖采样、不会因为群体偏斜而漂的来源，永远留一点做正则。

融合方式是加权平均到 `score`，再 `to_level()`；`combined` 与 `score` 偏差过大时校验器会 warn（`difficulty-weights`），防止权重表和数值对不上。

## 9. 怎么验收 / 校准

| 指标 | 目标 | 怎么测 |
| --- | --- | --- |
| 与人工标注 Spearman | ≥0.75 | 抽 50 题人工标，脚本算 |
| level 分布合理性 | L1:L2:L3:L4:L5 ≈ 1:2:3:3:1 | `--stats` 看直方图 |
| 跨来源一致性 | A 与 B Spearman ≥0.5 | 两路都算，比对 |
| 稳定性 | 重跑同一题 level 抖动 ≤1 级 | 随机 100 题重跑两次 |
| 常识抽查 | 明显送分题不得 ≥4 | 人眼过 20 题 |

**调参顺序**：先调量表措辞（B 的系统性偏差多半来自量表歧义）→ 再调 BASE/SPREAD（A 的偏差）→ 最后才动权重表。

## 10. 要把 C/D 跑起来，产品侧缺什么

`app/server.py` 的 `POST /api/result` 现在只收整卷聚合（`score/total/answer/duration_s`）。要补的最小改动：

```jsonc
// POST /api/result 增加一个可选字段
"items": [
  { "qid": "q03", "n": 3, "answer": "B", "correct": true,  "seconds": 42 },
  { "qid": "q04", "n": 4, "answer": null, "correct": false, "seconds": 0 }
]
```

- 前端 `TestRunner` 提交时把每题的选择、对错、用时一起带上；
- 服务端追加写 `results_items.jsonl`（**一行一条作答**，方便离线统计），保留每题 `qid`；
- 有了这个文件，Elo 就能批量更新，IRT 也就有了拟合数据。

不改这个，方案 C/D 永远只能停留在纸面。
